Model candidates

A Pythagoras card

Nick Ward

🧭 Purpose

Compare documented model configurations with the current outcome, predictor types, missing values and observation structure. Use this diagnostic card after data preparation and Observation resampling, before choosing a model to train.

The card displays recipes from the versioned capability catalogue. It does not fit, benchmark, install or automatically select a model, and it leaves incoming data and pipeline metadata unchanged until Commit is pressed.

🎯 Goals

  1. Primary: Find recipes that meet the current data requirements.
  2. Secondary: Explain exclusions, unknown capabilities and preparation requirements.
  3. Tertiary: Distinguish runtime evidence from documentation and expert judgment.

🧠 How it works

The outcome task comes from the upstream modeling context. Automatic inference uses a numeric Target for regression, a nominal or Boolean Target for classification, and an ordered categorical Target for ordinal classification. Numeric class codes need an explicit classification choice upstream. Without a resolved outcome, the card asks for a Target or an explicit task.

Only Predictor-role columns are inspected. Target and declared survival outcome components are excluded. Treatment, Identifier, Sequence, Geometry and Weighting columns are not silently added to the design matrix. Assign predictor roles intentionally when defining the analysis.

The card distinguishes missing numeric and missing categorical values. Boolean and ordered categorical predictors request categorical support; preserving ordinal order is a recipe-specific consideration. Infinite numeric values and unsupported types, such as raw datetime predictors, prevent a compatible match until prepared upstream.

Each row describes one joint configuration. A model that handles categories only after encoding is shown with its input requirements; capabilities from separate recipes are never combined. Readiness combines input and broader requirements: Meets requirements, specific preprocessing actions, unsupported requirements, or Untested. With excluded models hidden, every displayed row meets requirements. Evidence remains separate. Requirements describe the needed result, such as numeric representations or no missing values, without prescribing imputation or one-hot encoding. The flip-side separately records the specific tested preparation. Alternative techniques may satisfy the requirements, but are not validated by that recorded probe. Compatibility and evidence continue to refer to the complete tested recipe, not the bare estimator. Identifier repetition, Sequence and Geometry roles introduce longitudinal, temporal and spatial requirements. Content that merely looks like a date or coordinate does not establish those roles.

Status Interpretation
Meets requirements Current inputs and broader requirements meet the checks performed here.
Preprocessing: … Resolve the stated input conditions before fitting.
Does not support … A required capability is explicitly unsupported.
Untested: … At least one input condition, capability or structural use has not been reviewed.
Probe passed The recorded configuration passed small compatibility checks.
Documentation only Official documentation was reviewed; adapters and runtime probes remain outstanding.

Installation/version status is independent of these judgments. A missing optional package does not mean its model is analytically unsuitable. A matching package version does not validate an untested adapter.

🏞️ Front

The summary names the task, structural requirements and predictor count. The table shows model, input requirements, readiness, evidence, installation and scale guidance. Column filters help narrow the displayed rows. Fullscreen gives the table more vertical space.

The table columns are ordered: Model, Core mechanism, Composition, Fitting criterion, Transparency, Learning strategy, Prediction outputs, Scale, Input requirements, Readiness, Evidence, Package, Installation, and Recipes.

Each table row represents one method. Recipes counts the recipes remaining after the display filters. A single ranked recipe supplies the row’s readiness, evidence, requirements and installation status. Matching, validated recipes are preferred for the summary. Capabilities are never combined across recipes. On the flip side, expand each recipe to compare its own preparation, conditions and evidence. Enable Show excluded and unreviewed recipes to inspect alternatives hidden by the current requirements.

Select a row, then flip the card to inspect it. An empty table is explained in the footer. It may mean insufficient catalogue coverage rather than absence of suitable models in the wider ecosystem.

🔄 Flip side

The flip side presents the selected recipe in a shaded panel with a readable model name, a separate technical identifier, and distinct readiness and evidence badges. Input requirements, tested preparation, configuration, fitting instructions, conditions, assessment and references are grouped into sections. The panel scrolls in the compact card and uses additional columns when space permits in full-screen. Judgments are guidance, not measured accuracy or timing results.

Readiness combines current input and broader requirements; evidence describes the complete tested recipe. This card never trains models or executes preparation. Catalogue coverage is incomplete, and documentation-only recipes need adapters and runtime validation. A valid upstream resampling plan is needed before evaluation, but the catalogue remains browsable without one. Data-specific warnings, including weighting fallbacks, appear beside the front summary rather than in a separate flip-side Notes block.

🛠️ Controls and actions

  • Show excluded and unreviewed recipes: Include superseded, incompatible and unknown recipes for the current task, with reasons. Superseded entries name the broader method; the flip side explains parameter mappings and limitations. This is display grouping, not automatic model substitution. This does not list every unreviewed estimator in the raw inventory; entries need a recipe.
  • Show installed packages only: Hide packages absent from the current environment. Installed versions may still differ from the reviewed snapshot.
  • Use observation weightings: Require fitting-weight support when the assigned effective weights are valid and nonuniform. Invalid weights produce a visible unweighted fallback; this card does not apply weights or rebalance data.
  • Explore forecasting recipes: Browse forecasting contracts explicitly. Sequence supplies time-index metadata, but forecast horizons and lag windows still require a future adapter. A resampling window is not automatically a forecasting horizon.
  • Required prediction output: Request probabilities, survival risk, a forecast or prediction intervals. Unreviewed output support is shown as unknown.

Settings affect display and matching only and use ordinary card configuration persistence. There is no training or apply button.

🔎 Interpretation and next steps

Review preparation and assumptions before choosing a candidate. A survival risk ranking and a survival probability curve are different outputs. Spatial fitted values do not establish prediction support at new locations. A repeated-entity model may require different prediction rules for known and unseen subjects.

⛔️ Limitations

The catalogue is intentionally incomplete. Specialist recipes currently require integration work and runtime validation. Predictor summaries describe the current preview; preprocessing must be refitted within each training fold. A compatible row does not certify task assumptions, valid metrics, calibration, runtime, memory use or out-of-sample accuracy. The card does not infer a spatial weights matrix, forecast horizon or lag configuration. Evaluation readiness remains separate from browsing.

📌 Suggested workflow

  1. Assign roles and confirm outcome semantics upstream.
  2. Define and inspect an evaluation plan in Observation resampling.
  3. Review compatible recipes and their preparation.
  4. Show excluded/unreviewed recipes to understand coverage gaps.
  5. Inspect the selected recipe and validate it in the eventual training workflow.

🔗 Data flow

  • Input: Current predictors, stable outcome data, roles, modeling context and evaluation metadata, plus the JSON catalogue and installed-package metadata.
  • Output: Until commitment, the incoming proxy passes through unchanged. Commit adds an unfitted terminal estimator recipe to the pipeline and a Learning entry to the data journey; data values remain unchanged.
  • Data journey: No cleaning operation, learned transformation or evaluation plan is added. Display changes do not train models or start extended tasks.

🧭 Model characteristics

Six descriptive columns help compare methods: Core mechanism, Composition, Fitting criterion, Learning strategy, Prediction outputs, and Transparency. Use the column headings to sort the table. Scroll horizontally to reach additional columns; select a row and flip the card for explanations and sources. Sorting changes the view, not the data or model configuration.

  • Core mechanism permits combinations, such as Tree and Gen. linear. Gen. linear means linear / generalized linear, including linear predictors over transformed features. Distribution, rule, symbolic, prototype and specialist mechanisms are retained where the initial families do not describe a method.
  • Composition describes how components combine: a forest aggregates trees; a model tree routes to linear leaf models. Multiple labels can describe nested composition. A component’s transparency does not automatically transfer to its ensemble.
  • Fitting criterion distinguishes loss, regularization and split criteria in the details. It can be configuration dependent; some neighborhood methods do not optimize a fitting loss. Model-selection criteria are not fitting losses.
  • Learning strategy describes when the predictor is constructed. Eager methods fit a reusable model before prediction; Lazy methods defer local estimation or neighbor aggregation until each query; Hybrid methods combine both predictive mechanisms. Nearest-neighbor predictors are Lazy even when they build a search index or use ordinary preprocessing. Nearest-centroid, GP and SVM predictors are Eager: retaining training data or doing substantial prediction-time computation does not make a method lazy. Configurable wrappers say Depends on configuration until a recipe resolves their components. This is not a speed ranking, memory guarantee or incremental-learning flag. Sort this column and inspect the recipe details for its qualification.
  • Prediction outputs combines the former Formulation and Prediction outputs descriptions. Regression recipes show Point prediction or Point prediction & spread. Spread means a documented uncertainty output for individual predictions, such as predictive standard deviation, covariance, intervals or distribution samples; it does not certify calibration. Gaussian-process regression, Bayesian ridge and ARD regression provide point predictions and spread. Their details identify the output options and the meaning of that uncertainty. Ordinary linear-regression recipes remain Point prediction because these recipes return point predictions only. This is a recipe capability distinction: some other OLS implementations can calculate input-dependent prediction intervals. A single fitted quantile, coefficient standard errors, global residual variance or variation among ensemble members alone do not establish prediction-spread support. The flip side retains the precise output list, including quantiles and specialist outputs. Classification still distinguishes labels, scores and class probabilities. Use Required prediction output: Prediction spread to require spread support.
  • Transparency is expert guidance about the whole model: Usually transparent, Conditional, or Usually opaque. Complexity, transformed features and composition can change how understandable a fitted model is. It is not a measured score or a claim about post-hoc explanation tools.

Unreviewed, Not applicable, and Depends on configuration have distinct meanings. A method summary says Varies by recipe when its displayed recipes have different descriptions; inspect each recipe rather than pooling their capabilities. Readiness and evidence still describe the named summary recipe. The characteristics do not establish compatibility, installation, integration, or successful validation. Capacity growth is reserved for stage 2 and is not currently assessed or displayed as a filter.

Committing a model

Select a method and press Commit. The displayed summary recipe is committed, including its constructor parameters and supported preparation. The status beneath the button identifies the committed estimator and recipe. Browsing other rows does not change it. Recommit to replace the model; changing upstream data requires a fresh commitment.

Commit does not fit a model. The pipeline selects predictor-role columns before the estimator, excluding outcomes and other non-predictor roles. Supported preparation is fitted only when the pipeline is trained. Unvalidated, unavailable, or adapter-dependent recipes cannot be committed; the footer explains the reason and retains any previous commitment. Weighting requirements remain catalogue checks; training consumers must supply fit weights explicitly.
