Pipeline tuning

A Pythagoras card

Nick Ward

Tune the committed preprocessing pipeline and one committed model together, using the evaluation splits from Observation resampling when available, or reproducible implicit cross-validation when no plan is defined. Place Pipeline tuning after Model method candidates and Tuning parameters. Commit model and search choices before starting.

Search and objective

Choose one primary objective: classification supports balanced accuracy, accuracy, ROC AUC and log loss; regression supports RMSE, MAE and R². The objective label states whether it is minimized or maximized. All supported task metrics are recorded automatically without changing ranking. A secondary metric that cannot be evaluated is recorded as unavailable with a reason; its failure does not discard a successful primary evaluation. Scores for errors are displayed as positive errors; the internal sklearn scorer convention remains higher is better.

The committed finite choices from Tuning parameters are used directly. Additional model choices accepts a JSON object of complete sklearn parameter paths and finite lists, for example:

{"data_models__estimator__alpha": [0.1, 1, 10]}

These choices are combined with the committed grid. To change an already committed parameter’s choices, return to Tuning parameters. Constructor defaults are not search ranges. Fixed configuration, seeds, topology and weighting cannot be tuned.

  • Random samples unseen finite configurations.
  • Exhaustive evaluates each finite configuration.
  • Bayesian TPE adapts proposals using completed evaluations. Optuna is included in the native Python project dependencies; no separate extra is needed.
  • Bayesian GP (skopt) uses a Gaussian-process surrogate of the search objective. It proposes finite parameter choices through scikit-optimize; it does not restrict the type of predictive model being tuned. The surrogate minimizes the negative of the internal higher-is-better primary score. Failed trials are excluded from surrogate fitting, without fabricated penalties; an out-of-grid starting configuration is not included as surrogate evidence. Duplicate proposals use an unseen fallback configuration. All actual completed choices remain the recorded history.

Each committed method is evaluated first as a starting configuration, even if its values are outside its search choices. Candidate budgets exclude these starting configuration evaluations. Maximum candidates applies to every search method. Zero means no candidate limit; a positive value caps candidate trials across resumes. Unlimited searches still stop when the finite search space is exhausted or the time limit is reached. There is no separate exhaustive-cap switch. Grid coverage counts the starting configuration when it matches a grid configuration, without fitting that configuration twice. Partial exhaustive searches report completed grid configurations and failures separately. “Finished” means all grid choices have been visited, not that all succeeded. All budgets are cumulative across resumes. A zero time budget means unlimited time; time budgets are checked between folds, so an individual fit can exceed the remaining time.

Progress and comparison

The front states the best parameters found so far, their mean objective value and improvement over starting configuration. The chart shows only completed trial mean scores as points, without error bars, ranges, reference lines or connecting lines. When multiple model methods are selected, a consistent color and legend entry identify each method. Colors follow the committed candidate order and remain stable as trials complete. Hover text identifies the method and whether the trial is a starting configuration or candidate. Trial numbers are one-based. Parameters are only committed when you explicitly accept a completed row. All settings have guided explanations.

The flip side lists configurations, states, scores, fold standard deviations, times, model identity and failures. Incomplete or failed evaluations are not ranked or eligible for acceptance. All secondary metrics and their failure reasons appear in the table and CSV. JSON checkpoints include fold results, parameters, search identity, versions and continuation state.

Pause, cancel and resume

Pause stops scheduling new work and lets active fits finish. Cancel current tuning terminates outstanding fit processes. Completed fold results are retained; Resume retries only missing work. Estimator thread controls (n_jobs, thread_count, nthread, num_threads, where exposed) and supported BLAS/OpenMP pools are limited to one per fit to avoid nested oversubscription. Otherwise-unseeded estimators receive the search seed; the accepted configuration includes these fixed settings.

Save a checkpoint before closing a session. Checkpoints are also included in the card’s bookmark configuration state, but running processes are not restored automatically. Checkpoints use schema version 4; earlier checkpoints must be replaced by a new search. Load the JSON with the same data, pipeline, choices, model, objective, seed, splits and software versions. Increase the candidate or total-time budget and press Resume. These budgets do not change the search identity. TPE proposals use the actual recorded history and a deterministic seed derived from the search seed and trial count; no optimizer pickle is loaded.

Changing data, the pipeline or search settings makes old results stale. They remain visible for review, but cannot be resumed or accepted against the changed inputs. Restoring the original inputs makes a compatible checkpoint usable again.

Accept a result

On the flip side, select a completed row and press Accept selected. This commits fixed parameter values to an unfitted outgoing pipeline and records a Learning step in Data journey. Searching alone never changes the exported parameters. Revert acceptance restores the incoming settings. Acceptance does not perform a final development-data fit or evaluate the final holdout.

Every candidate is cloned and fitted on raw post-cleaning training-fold rows. Full-data previews are not used for training. Final holdout and prediction observations are excluded from all search fits and scores. The best search score is a model-selection result and can be optimistic; use a separate final evaluation for an assessment of generalization.

This first version runs on the native Python server, supports committed regression or classification candidate methods, and rejects weighted data pending an explicit row-aligned fitting/scoring adapter. Successive halving and within-fit training curves are reserved for later versions. Invalid parameter combinations are reported as failed candidates without losing completed results.

Upstream or implicit resampling

Every search method reuses a defined upstream evaluation plan exactly, preserving its group/time restrictions and holdout/prediction exclusions. An invalid or stale plan must be corrected; it is never silently replaced by implicit CV.

If no plan is defined, searches generate shuffled five-fold CV with the search seed. Classification stratifies by target; regression uses K-fold. The fold count is reduced to the available number of observed targets and, for classification, the smallest observed class count. At least two folds and two classes are required for classification. Missing-target rows are reserved for prediction and excluded from every fit and score. No final holdout is invented.

This automatic fallback assumes independent rows. Assigned Partition, Sequence, Geometry or Stratifier roles, or repeated Identifiers, require an explicit upstream plan so their intended boundaries are not guessed. The implicit split strategy and origin are shown in progress and included in the search fingerprint and checkpoint specification. Splits remain fixed across candidates and resumes. Generating an implicit search plan does not modify the upstream source or commit an evaluation plan to it. A selected estimator that itself uses CV retains that internal behavior; search CV is an additional outer evaluation layer, not a switch disabling its CV.

Bayesian GP uses skopt.Optimizer ask/tell rather than handing evaluation to BayesSearchCV. This preserves our fold checkpoints, cancellation and explicit acceptance. scikit-optimize is installed with the native project dependencies. Its state is reconstructed from actual completed in-grid trials; only JSON history is saved, not a serialized optimizer.

The chart updates when a trial completes evaluation. Elapsed-time updates and progress status changes do not redraw already completed trial scores. The table and progress can continue updating independently while fits run.

Parallel execution

Auto (the card default) evaluates starting configuration folds concurrently, then runs concurrent candidate trials when more than one configuration remains. If only one configuration remains, it uses parallel folds. Trials runs several configurations concurrently with sequential folds inside each. Folds evaluates one configuration at a time with concurrent folds. Sequential runs one fit at a time. Exact upstream or implicit split memberships are unchanged by scheduling.

Maximum simultaneous fits is the worker-process limit. Zero chooses half the available CPUs, rounded down, with at least one worker. Requests are bounded by detected CPU availability and an estimated per-fit memory footprint, including dense GP covariances, against one quarter of physical RAM. This is a conservative heuristic, not a hard memory limit; large one-hot expansions and custom transformers may need a smaller manual limit. Progress and the specification show the effective count.

Bayesian searches propose deterministic batches and wait for the batch to finish before proposing the next. Skopt uses batch ask with constant-liar proposals; TPE accounts for pending candidates. Temporary optimizer estimates are not persisted as real scores. Changing worker count or execution mode changes search identity and can change Bayesian proposals. Extending a candidate budget after a short batch can also change the subsequent Bayesian path compared with a search started with a larger budget. Resuming an unchanged recorded batch preserves its proposals.

Checkpoints store completed fold IDs, so out-of-order results and multiple unfinished trials can resume without repeating reported fits. Charts update only for completed trial scores.

The total time limit measures cumulative wall time, including pool startup and optimizer work. The candidate table’s Seconds sums work time across its fold tasks, so overlapping fits can total more than the overall wall time. Pause and time limits let active fits finish without launching replacements. Cancel terminates outstanding workers; worker crashes report an error and leave an indexed checkpoint that can retry missing work.

Upstream repeated K-fold plans evaluate every repeat. Progress states the repeat/fold counts, and checkpoints retain a repeat/fold descriptor for each evaluated split. The chart plots the mean across all evaluated splits; uncertainty comparisons remain in the separate Bayesian comparison table.

Bayesian practical-equivalence comparisons

The flip side offers pairwise Bayesian comparisons following sklearn’s worked example. Supply a positive Practical-equivalence tolerance in absolute primary-metric units. For accuracy, 0.01 means one percentage point; for MAE it means 0.01 response units. This choice should reflect application needs, ideally set before inspecting results. No tolerance is assumed automatically.

The comparison uses every pair among the top five completed trials by default; Top trials to compare permits 2–20. The starting configuration participates when ranked into that shortlist. Failed, incomplete or unaligned results are excluded. Positive Mean advantage A always favors trial A, including metrics minimized as errors. The table reports probabilities of A being better beyond the tolerance, the pair being within the tolerance, and A being worse beyond it, plus a 95% credible interval for mean advantage. The decision label defaults to a 0.95 posterior probability threshold; otherwise it is Inconclusive. Acceptance remains manual.

These comparisons require an upstream repeated shuffled ordinary or stratified K-fold plan. They use aligned fold-level score differences, a Student-t posterior with n - 1 degrees of freedom, and scale sqrt((1/n + mean(n_validation/n_training)) * sample_variance(differences)), where n counts all paired splits. The mean size ratio accommodates near-balanced folds and is an approximation. The dependence correction is retained: avoiding multiple-comparison p-value corrections does not make CV splits independent. Group-dependent and temporal plans are outside this implementation’s assumptions.

Repeat/fold identities are retained. Repeat advantage SD is the sample SD of the mean paired differences for each repeat. It describes sensitivity to repartitioning, not a standard error or spread across independent datasets. The posterior calculation follows the fold-level corrected example; it does not treat repeat means as independent samples. Zero paired-score variability cannot support a nondegenerate posterior here and is reported as unavailable.

Probabilities are exploratory, conditional on the approximation and observed search results; they do not remove tuning-selection bias and are not probabilities that a trial is globally best. No Bonferroni p-value correction, automatic acceptance, new fits or final-holdout access is introduced. Comparison controls do not change search identity, budgets or chart points. Comparisons can be downloaded as CSV.

Searching alternative modeling methods

With several committed candidates, each trial chooses a method and only that method’s parameter grid. Shared preprocessing choices apply to every method. Every method receives one starting configuration evaluation using its committed values; the Maximum candidates budget is global and excludes all method starting configurations. The progress display states how many starting configuration evaluations are required. Time limits cover the complete search. Matching in-grid starting configurations are counted once.

Random and Exhaustive visit the union of valid branches. TPE and skopt use separate optimizers for each method with deterministic balanced allocation between non-exhausted methods. No inactive-method parameter values or fictitious objective scores are supplied. All methods reuse identical CV memberships, fit preparation inside each fold, and obey the same parallel-fit limit. Method/recipe IDs remain part of checkpoint identity, and resuming preserves reserved branches and results.

The flip-side table and CSV include a Method column, with recipe identity in Model. Chart hover text and the best-result statement identify the method. Improvement over starting configuration uses that method’s own starting configuration. Accepting a completed trial publishes its method/preparation and parameter values together as an unfitted pipeline. Revert restores the incoming candidate set. Statistical comparisons can compare different methods because their metric and split identities match.

After acceptance, downstream training and tuning use the accepted method and its fixed settings. The original candidate collection remains available as metadata; recommit a candidate set in Model candidates to search across alternatives again.

The chart x-axis is labeled Trial. Diamond markers identify each method’s committed starting configuration; circles identify tuned candidates. Method colors are preserved for both shapes. Starting configurations use the same CV splits as candidates, remain eligible for acceptance, and provide the reference for the displayed improvement. They are not null models. The candidate budget excludes one starting-configuration evaluation per method.
