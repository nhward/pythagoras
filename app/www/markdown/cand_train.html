Pipeline training

A Pythagoras card

Nick Ward

Train the combinations of hyper-parameters and model-methods and record the score based on the chosen metric. A chart shows the extent of the training task along its X-axis. Training progress appears as additional bars in the chart. The training is undertaken in a multi-process and multi-threaded context to maximize training evaluation.

This card is about managing the calculation and evaluation of combinations. This card is not for choosing the absolute-best configuration as this may depend on more than just a single score.

Upstream cards

This card relies upon upstream cards:

  • Observation resampling for a resampling plan. Without a plan, searches use seeded five-fold CV (target-stratified for classification), with fewer folds for small datasets.
  • Model method candidates for modeling methods that are appropriate for any prediction task. More than one candidate method can be selected. The pipeline training cannot proceed without at least one method.
  • Tuning parameters The upstream cards (including the model method candidates card) are interrogated for any hyper-parameters. The selected hyper-parameters will create combinations (trials) that will be trained in this card. If there are no hyper-parameters selected, the training will be merely a single trial for each modeling-method.

Scoring

The score appears as the height of each bar in the chart.

Choose one primary objective:

  • classification supports balanced accuracy, accuracy, ROC AUC and log loss
  • regression supports RMSE, MAE and R².

The objective label states whether it is minimized or maximized. All supported task metrics are recorded automatically. Any metric that cannot be evaluated is recorded as unavailable with a reason. Scores for errors are displayed as positive errors; the internal sklearn scorer convention dictates higher is better.

The search uses only the choices committed by the upstream Tuning parameters card. Edit parameter choices there, then commit them before training. Without a committed grid, training evaluates each configured model method once using method defaults.

Search method

The valid combinations of hyper-parameters and modeling-methods form a finite set. While finite, this may still be a unfeasibly large set of combinations.

  • Random samples the combinations and halts when the time-limit or trial-limit is reached. There is no guarantee that the best combination has be encountered yet.
  • Exhaustive evaluates each finite configuration in a repeatable order. It can only be manually halted.
  • Bayesian TPE adapts proposals using completed trials and halts when the time-limit or trial-limit is reached. There is no guarantee that the best combination has be encountered yet but it is more likely than the Random method.
  • Bayesian GP uses a Gaussian-process surrogate of the search objective. It proposes finite parameter choices through scikit-optimize. As with Bayesian TPE it adapts proposals using completed trials and halts when the time-limit or trial-limit is reached. There is no guarantee that the best combination has be encountered yet but it is more likely than the Random method.

Running

The ▶️ button starts the training of the pipeline. Evaluation of the combinations (i.e. pipeline training and testing) will continue until one of the following:

  • The last of the combinations is reached - status “Finished”
  • The pause button (or cancel button) is pressed - status “Halted”
  • The configured time limit is reached (e.g. 600 seconds) - status “Halted” (This does not apply to “Exhaustive”)
  • The configured combination limit is reached (300 combinations) - status “Halted” (This does not apply to “Exhaustive”)

Each committed method is evaluated first as a starting configuration. Candidate budgets exclude these starting configuration evaluations.

Exhaustive ignores both combination and time budgets and evaluates every finite configuration unless manually paused or cancelled. Maximum candidates and Maximum time budget apply to the other search methods. Zero means no limit; a positive value caps trials across resumes.

“Finished” means all grid choices have been visited, not that all succeeded. For non-exhaustive searches, budgets are cumulative across resumes. A zero time budget means unlimited time; time budgets are checked between folds, so an individual fit can exceed the remaining time.

Progress and comparison

The front states the best parameters found so far, their mean objective value and improvement over starting configuration. The chart shows only completed trial mean scores as bars. When multiple model methods are selected, a consistent color and legend entry identify each method. Colors follow the committed candidate order and remain stable as trials complete. Hover text identifies the method and whether the trial is a starting configuration or candidate. This card publishes tuning evidence without changing the incoming pipeline. Choose a best-model downstream.

The flip side lists configurations, states, scores, fold standard deviations, times, model identity and failures. Incomplete or failed evaluations are not ranked. All secondary metrics and their failure reasons appear in the table. Bookmarks include training checkpoints with fold results, parameters, search identity, versions and continuation state.

Pause, cancel and resume

Pause stops scheduling new tasks and lets active tasks finish. It preserves completed folds, trial history and elapsed time so Play can continue.

Cancel current tuning stops outstanding tasks and discards all trials, chart history, saved checkpoint and elapsed progress. Play then starts from scratch. Use Pause when you intend to continue, and Cancel when you intend to start over.

Play resumes a compatible checkpoint, preserving the bars and completed fold results. Exhausted history is retained: use Cancel to clear it before starting a new search. A budget-limited search can continue after increasing its cumulative trial or time budget.

To continue in a later session, Pause training and save a bookmark. Restore the bookmark, then press Play to resume. Bookmarks include card settings and the portable training checkpoint, including completed fold results, parameters, search identity, versions and continuation state. Running processes are not restored automatically. Compatibility depends on the effective training data, pipeline, choices, model, objective, seed, splits, software versions and declared training compatibility version. Whole-file hashes are retained for audit but presentation and widget edits do not invalidate training. For non-exhaustive searches that reached a budget, increase the candidate or time budget before pressing Play. Budgets do not change search identity; Exhaustive ignores both limits. TPE proposals use the actual recorded history and a deterministic seed derived from the search seed and trial count; no optimizer pickle is loaded.

Older or mismatched progress remains available after bookmark restoration. Play shows a compatibility warning with Resume anyway. This explicit override retains completed scores and their previous specification, restarts unfinished trials, and records the override in the bookmark. A persistent warning notes that earlier and new scores may not be comparable. Checkpoint structure is still validated: incompatible model identities, parameter grids, metrics or evaluation layouts may require a new search. Cancelling the warning leaves history untouched. Restoring the original inputs can also make a checkpoint compatible again.

Upstream or implicit resampling

Every search method reuses a defined upstream evaluation plan exactly, preserving its group/time restrictions and holdout/prediction exclusions. An invalid or stale plan must be corrected; it is never silently replaced by implicit CV.

If no plan is defined, searches generate shuffled five-fold CV with the search seed. Classification stratifies by target; regression uses K-fold. The fold count is reduced to the available number of observed targets and, for classification, the smallest observed class count. At least two folds and two classes are required for classification. Missing-target rows are reserved for prediction and excluded from every fit and score. No final holdout is invented.

This automatic fallback assumes independent rows. Assigned Partition, Sequence, Geometry or Stratifier roles, or repeated Identifiers, require an explicit upstream plan so their intended boundaries are not guessed. The implicit split strategy and origin are shown in progress and included in the search fingerprint and checkpoint specification. Splits remain fixed across candidates and resumes. Generating an implicit search plan does not modify the upstream source or commit an evaluation plan to it. A selected estimator that itself uses CV retains that internal behavior; search CV is an additional outer evaluation layer, not a switch disabling its CV.

Bayesian GP uses skopt.Optimizer ask/tell rather than handing evaluation to BayesSearchCV. This preserves our fold checkpoints, cancellation and evidence publication. Its state is reconstructed from actual completed in-grid trials; only JSON history is saved, not a serialized optimizer.

Bayesian TPE and Bayesian GP also learn fit feasibility separately from performance. After at least four in-grid observations including both successful fits and classified fit failures, a small classifier weights proposed configurations by their estimated chance of fitting successfully. Failed fits receive no invented score. Proposal acceptance retains a 10% exploration floor and bounded retries, so suspected problem regions remain searchable. Random and Exhaustive are unchanged. Execution/resource failures, schema lookup failures and unclassified errors are excluded from feasibility learning. Older failures without a recorded classification are also excluded. When every fit fails, search continues exploring because there is no successful region to learn. The classifier is rebuilt from recorded history on resume; it is not saved as a fitted model.

Result refresh interval (seconds) controls how often completed results are published while tuning (default: five seconds; zero publishes every completed update). The chart, best-result statement and downstream Model candidates evidence share the same snapshot. Continuous completions do not postpone the next refresh. Final results are published promptly when tuning stops. The candidate table uses the same refresh interval, while progress and worker communication remain frequent. This setting is saved with the card and does not change the search identity.

The history chart keeps its existing widget and method traces. Its x-axis spans the finite combination count plus starting configurations. The initial y-axis spans zero to twice the first completed score (with a nonzero fallback for a zero score), and expands only if a later score falls outside that range. New results update existing point arrays rather than creating another chart widget.

Parallel execution

Auto (the card default) evaluates starting configuration folds concurrently, then runs concurrent candidate trials when more than one configuration remains. If only one configuration remains, it uses parallel folds. Trials runs several configurations concurrently with sequential folds inside each. Folds evaluates one configuration at a time with concurrent folds. Sequential runs one fit at a time. Exact upstream or implicit split memberships are unchanged by scheduling.

Maximum simultaneous fits is the worker-process limit. Zero chooses half the available CPUs, rounded down, with at least one worker. Requests are bounded by detected CPU availability and an estimated per-fit memory footprint, including dense GP covariances, against one quarter of physical RAM. This is a conservative heuristic, not a hard memory limit; large one-hot expansions and custom transformers may need a smaller manual limit. Progress and the specification show the effective count.

Bayesian searches propose deterministic batches and wait for the batch to finish before proposing the next. Skopt uses batch ask with constant-liar proposals; TPE accounts for pending candidates. Temporary optimizer estimates are not persisted as real scores. Changing worker count or execution mode changes search identity and can change Bayesian proposals. Extending a candidate budget after a short batch can also change the subsequent Bayesian path compared with a search started with a larger budget. Resuming an unchanged recorded batch preserves its proposals.

Checkpoints store completed fold IDs, so out-of-order results and multiple unfinished trials can resume without repeating reported fits. Charts update only for completed trial scores.

The total time limit measures cumulative wall time, including pool startup and optimizer work. The candidate table’s Seconds sums work time across its fold tasks, so overlapping fits can total more than the overall wall time. Pause and applicable time limits let active fits finish without launching replacements. Cancel terminates outstanding workers and clears search history; worker crashes report an error and leave an indexed checkpoint that can retry missing work.

Upstream repeated K-fold plans evaluate every repeat. Progress states the repeat/fold counts, and checkpoints retain a repeat/fold descriptor for each evaluated split. The chart plots the mean across all evaluated splits; uncertainty comparisons are available downstream in Model candidates.

Downstream candidate review

Completed tuning results now pass through proxy_data to Model candidates, including unfitted pipelines, split scores, compact out-of-fold error summaries and observed prediction timing. This card publishes evidence without selecting a configuration. Practical-equivalence tolerance, per-method shortlist size and comparison decision probability belong to Model candidates. The tuning chart remains a points-only search-progress display. Old results lacking prediction evidence require a new search to populate downstream error-risk and speed diagnostics.

Searching alternative modeling methods

With several committed candidates, each trial chooses a method and only that method’s parameter grid. Shared preprocessing choices apply to every method. Every method receives one starting configuration evaluation using its committed values; the Maximum candidates budget is global and excludes all method starting configurations. The progress display states how many starting configuration evaluations are required. For non-exhaustive methods, time limits cover the complete search. Matching in-grid starting configurations are counted once.

Random and Exhaustive visit the union of valid branches. TPE and skopt use separate optimizers for each method with balanced allocation with seeded random tie-breaking between non-exhausted methods. After the starting configurations, methods with the fewest attempts are chosen first, with their order randomized when tied. Attempts are balanced per method, not proportional to each method’s grid size; exhausted methods are skipped. The saved seed and RNG state preserve the sequence when resuming. No inactive-method parameter values or fictitious objective scores are supplied. All methods reuse identical CV memberships, fit preparation inside each fold, and obey the same parallel-fit limit. Method/recipe IDs remain part of checkpoint identity, and resuming preserves reserved branches and results.

The flip-side table includes a Method column, with recipe identity in Model. Chart hover text and the best-result statement identify the method. Improvement over starting configuration uses that method’s own starting configuration. This card preserves the incoming pipeline and candidate set, and publishes completed trial evidence for downstream model selection. It does not accept or revert configurations. Statistical comparisons can compare different methods because their metric and split identities match.

The chart x-axis is labeled Trial. Hatched bars identify each method’s committed starting configuration; solid bars identify tuned candidates. Method colors are preserved for both bar styles. Starting configurations use the same CV splits as candidates, remain available for downstream selection, and provide the reference for the displayed improvement. They are not null models. The candidate budget excludes one starting-configuration evaluation per method.

Memory and portable configurations

Only scores, settings and bounded review summaries accumulate across trials. Full predictions, duplicated outcomes, validation positions and probability matrices are not retained. Unfinished validation losses use temporary compressed arrays and are deleted once the trial’s exact tail summaries/101-point curves are computed. One unfitted pipeline template is shared per method.

Completed configurations need no prediction-evidence files. Saving a paused search embeds only its unfinished compressed arrays; restoration validates and isolates them for that configuration. No host paths are saved. Browser/shinylive restoration does not require native filesystem access, and larger configurations stage through IndexedDB during reload. Progress uses a bounded incremental queue. Starting a new search or ending the session releases its temporary evidence. Older row-level evidence is discarded on import; scores are preserved, but start a new search to use the current implementation’s compact diagnostics.
